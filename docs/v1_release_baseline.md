# V1 版本锁定说明

本文用于锁定当前 `clinical-data-system` 的 `V1` 版本边界，作为后续开发、测试、交付和版本管理的统一基线。

## 1. V1 定位

`V1` 表示当前已经完成首轮迁移并可在 Linux 服务器上交付给临床部门试用的版本。

本版本的目标不是一次性完成所有长期优化，而是先形成一套：

- 可部署
- 可上传 PDF 资料包
- 可完成 OCR 识别
- 可支持前后端联调
- 可继续在 Mac 本地迭代开发

的稳定基线。

## 2. 环境分工

### 2.1 Mac 本地环境

Mac 环境作为后续主要开发和测试环境，职责包括：

- 后端开发与联调
- 前端功能与交互优化
- 数据库结构设计与迭代
- 资料包处理逻辑优化
- 权限、主数据、业务流程的持续开发

Mac 本地 OCR 已切换为 **macOS 原生 Apple Vision OCR 服务**，作为开发测试用途，不再依赖 Docker 内的 PaddleOCR CPU 容器。

当前原则：

- Mac 不作为正式交付环境
- Mac 侧 OCR 通过 Apple Vision/CoreML 系统能力服务本机样本调试，不暴露 `gpu:0` 这类 Paddle 设备名
- Mac 侧 OCR 只要求功能正确、便于开发调试，并保持后端默认 OCR 地址不变
- 本地允许继续优化接口、前端、数据结构和流程

### 2.2 Linux 生产环境

Linux 环境作为当前 `V1` 的正式交付环境，职责包括：

- 提供前端页面给临床部门使用
- 提供后端 API
- 提供 OCR 服务
- 存放数据库和文件存储

Linux 生产环境中的 OCR 使用 **GPU 模式**。

## 3. V1 生产 OCR 基线

当前已经验证通过的生产 OCR 组合如下：

- `PaddlePaddle GPU`: `3.3.1`
- `PaddleOCR`: `3.3.1`
- CUDA wheel 源：`cu129`
- Linux 生产 OCR 运行方式：`gpu:0`

已经验证成功的结论：

- OCR 服务可正常启动
- `/health` 返回正常
- Paddle 在容器内识别为 `compiled_with_cuda=True`
- Paddle 运行设备为 `gpu:0`
- 实际 PDF 上传后可完成 OCR
- 不再出现 `Unsupported GPU architecture`

## 4. V1 部署原则

### 4.1 Linux 生产部署原则

V1 生产环境采用 **离线镜像包 + 离线模型缓存包** 的方式交付。

生产侧原则：

- 服务器不依赖在线 build GPU OCR 镜像
- 服务器优先使用本地 `docker load` 导入镜像
- OCR 模型缓存通过压缩包迁移
- GPU Compose 覆盖文件直接引用本地镜像，不在服务器重新 build

### 4.2 OCR 镜像与缓存

V1 对应的已验证离线 GPU 包产物为：

- `clinical-data-gpu-images-20260509-paddle331-cu129.tar.gz`
- `paddle-ocr-model-cache-20260509-paddle331-cu129.tar.gz`
- `SHA256SUMS-20260509-paddle331-cu129.txt`

如果后续生产继续沿用 V1，不应再退回旧的 `3.2.0 + cu118` 方案。

## 5. V1 代码与配置关键点

### 5.1 Mac 开发基线

Mac 本地开发环境使用 macOS 原生 Apple Vision OCR 服务，用于开发验证。

换句话说：

- 本地不再启动 Docker 内的 PaddleOCR CPU 容器
- 本地 OCR 服务继续占用 `8048`，后端 `PDF_PACKET_OCR_API_URL=http://127.0.0.1:8048` 不需要修改
- `/health` 返回的 `service` 应为 `mac-vision-ocr-api`
- Apple Vision OCR 没有 PaddleOCR 的 `gpu:0` 显式设备名，但会由 macOS 的 Vision/CoreML 系统框架调度
- 本地以“正确性”和“便于开发”为优先

当前本机验证结果：

- `010005.pdf` 全 27 页 OCR 已跑通，耗时约 12.6 秒
- 失败资料包重新分析后状态为 `ready`
- 已生成 `9 segments` 和 `27 text/OCR pages`

补充说明：

- PaddleOCR 的 Python Paddle 路线在 macOS 上没有可直接启用的 Apple GPU 开关
- 生产环境仍以 Linux GPU PaddleOCR 为准，本机 Apple Vision OCR 不替代生产基线

### 5.2 Linux 生产基线

Linux 生产环境必须保留以下事实：

- OCR 容器使用 `paddle-ocr-api-gpu` 新镜像
- GPU Compose 覆盖文件使用 `image` 而不是 `build`
- 模型缓存目录已经迁移到 `/root/.paddlex` 与 `/root/.cache/paddle`
- OCR 服务启动时会做预热与真实健康检查

### 5.3 前端上传行为

由于 PDF 资料包上传会同步执行 OCR 和识别，前端不能继续使用默认短超时。

V1 基线中已经包含：

- 资料包上传请求超时延长
- 资料包重新识别请求超时延长

这样可以避免“页面提示上传失败，但刷新后记录已经存在”的假失败现象。

## 6. V1 已知边界

`V1` 不是最终形态，以下事项属于后续持续优化范围，而不是本次锁定范围：

- 前端交互体验优化
- 资料包识别链路的性能优化
- 数据库结构继续演进
- 资料项自动匹配策略优化
- 后端接口补充与重构
- 开发环境体验优化

这些优化都应基于 `V1` 基线继续演进，而不是回退生产 OCR 方案。

## 7. V1 后续开发原则

后续推荐采用以下工作方式：

1. Mac 作为主开发与测试环境，继续跑 Apple Vision OCR。
2. Linux 保持当前已验证通过的 GPU 生产版本，供临床部门使用。
3. 所有结构性变更先在 Mac 完成开发与验证。
4. 需要交付生产时，再基于 Linux 生产方案做一次定向打包与迁移。

## 9. V1 生产变更与升级策略

本章节用于约束生产环境在后续迭代中的更新方式，避免“开发方便但生产不可控”的情况。

### 9.1 小范围前端改动

适用场景：

- 页面文案调整
- 前端交互优化
- 样式修正
- 前端请求超时、提示文案等轻量逻辑修复

推荐方式：

1. 在 Mac 本地完成前端修改和验证。
2. 重新构建前端发布物或重新构建前端镜像。
3. 仅替换生产环境前端相关文件或前端容器。
4. 重启前端服务使改动生效。

原则：

- 前端改动不应直接修改生产数据库
- 前端小改优先走“局部替换 + 前端重启”
- 如果只是替换静态资源，必须确认浏览器缓存不会导致旧页面残留

### 9.2 小范围后端改动

适用场景：

- 接口逻辑修复
- OCR 调用逻辑优化
- 权限判断修复
- 上传、识别、状态流转的小范围代码调整

推荐方式：

1. 在 Mac 本地完成功能验证。
2. 只替换后端相关文件，或重新构建后端镜像。
3. 重启 `backend` 服务使改动生效。
4. 如果改动依赖配置变化，同时同步 `backend.env` 或相关配置文件。

原则：

- 后端 Python 代码替换后，必须重启后端容器或进程，否则不会生效
- 如果后端改动涉及 OCR 行为，但 OCR 服务代码没变，不需要重建 OCR 容器
- 如果后端改动会影响上传、拆解、识别或数据入库，生产前必须用真实样本做一次回归验证

### 9.3 数据库新增表或轻量结构变更

适用场景：

- 新增表
- 新增字段
- 新增索引
- 小范围非破坏性结构扩展

推荐方式：

1. 在 Mac 本地完成 Alembic migration 编写与验证。
2. 在生产变更前先备份数据库。
3. 将 migration 代码同步到生产环境。
4. 通过后端容器启动时的 `alembic upgrade head`，或手动执行 Alembic 完成升级。
5. 升级后验证：
   - 表结构正确
   - 旧数据仍可读
   - 新功能可正常写入

原则：

- 新增表和新增字段属于“可控升级”，不应直接手工改生产数据库
- 必须通过 migration 管理，而不是线上临时 SQL 拼改
- 任何数据库结构升级前都要先做备份

### 9.4 少量文件直接替换的原则

当前实际工作方式中，少量文件修改通常是：

- 在本地改好相关文件
- 打包这些文件
- 直接替换生产环境对应原文件

这种方式可以继续使用，但必须区分“替换后是否需要重启”：

- 前端静态文件替换后：需要重启前端容器或确认 Nginx 已读取新内容
- 后端 Python 文件替换后：必须重启后端容器
- OCR 服务 Python 文件替换后：必须重启 OCR 容器
- Compose、env、Dockerfile 替换后：通常需要重新创建对应容器
- 数据库 migration 文件替换后：还必须执行数据库升级流程

换句话说，**替换文件本身不等于生效**，生产必须补上对应的服务重启或升级动作。

### 9.5 大版本迭代或大范围重构

适用场景：

- 前后端大版本升级
- OCR 方案切换
- 数据库大规模重构
- 文件存储路径规则变更
- 模块级架构调整

这类变更不能继续只靠“替换几个文件”完成，必须按完整升级流程处理。

推荐流程：

1. 先在 Mac 本地完成开发、联调、测试和迁移验证。
2. 明确升级范围：
   - 前端是否变
   - 后端是否变
   - OCR 是否变
   - 数据库结构是否变
   - 文件存储规则是否变
3. 生成独立升级说明文档。
4. 在生产升级前，先备份：
   - PostgreSQL 数据库
   - `runtime/file-storage`
   - `runtime/paddle-ocr/model_cache`（如有必要）
   - 当前部署配置文件
5. 使用新的镜像包、代码包或迁移包做完整升级。
6. 升级完成后做回归验证。
7. 保留回滚入口，确认无误后再清理旧版本。

### 9.6 如何保证生产数据不丢失

后续任何生产升级都必须遵守以下底线：

- 不直接删除生产数据库目录
- 不直接覆盖未备份的数据库
- 不直接清空 `runtime/file-storage`
- 不在未确认 migration 可执行的情况下先替换全部代码

生产数据保护的最低要求：

1. 升级前导出数据库 SQL 备份
2. 升级前备份文件存储目录
3. 如果升级涉及数据库结构，先确认 migration 是“向前兼容”或已准备回滚方案
4. 如果升级涉及文件路径规则变化，必须准备数据迁移脚本或兼容逻辑

### 9.7 数据库大重构时的原则

如果后续出现数据库大型重构，例如：

- 表拆分
- 主外键关系重建
- 枚举或字典体系重构
- 历史数据模型迁移

则必须采用“双重保障”方式：

1. 先备份生产库
2. 在测试环境用生产数据副本验证 migration
3. migration 必须具备明确顺序
4. 旧代码与新结构不兼容时，要安排停机窗口或灰度切换
5. 升级完成后立即做数据一致性检查

原则上，大重构不应在生产环境直接边改边试。

### 9.8 V1 阶段推荐的实际操作方式

结合当前阶段，推荐这样执行：

- 前端小改：替换前端相关文件或重建前端镜像，重启前端
- 后端小改：替换后端代码或重建后端镜像，重启后端
- OCR 改动：替换 OCR 服务代码或镜像，重启 OCR 容器
- 新增表/字段：通过 Alembic migration 升级，升级前先备份数据库
- 大版本迭代：按完整升级包和升级文档执行，不走零散热替换

### 9.9 V1 到后续版本的管理建议

从版本管理角度，建议后续采用以下分层：

- `V1`：当前已验证可交付基线
- `V1.x`：在 `V1` 基线上的小幅增强和修复
- `V2`：涉及架构、数据库或部署方式明显变化的新阶段

这样做的目的是：

- 让临床生产环境始终对应一个清晰基线
- 让 Mac 本地开发可以持续前进
- 让每次生产升级都有可追踪的版本边界
