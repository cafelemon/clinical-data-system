# 版本与进度文档

本文是 `clinical-data-system` 的唯一进度源，用于记录版本命名、阶段边界、验收状态、当前风险和下一步计划。

轻量版本时间线见 `docs/version_history.md`，该文件只记录版本号、日期和一句话摘要；详细范围和验收仍以本文为准。

## 1. 版本命名

### 1.1 对外版本

正式版本采用四段式：

```text
主版本.次版本.修订版本.构建号
```

示例：

- `1.0.0.x`：V1 基本框架和首个交付基线。
- `2.0.0.x`：V2 PDF 在线审阅和整改闭环。
- `2.1.0.x`：V2.1 审核工作台 UI 优化。
- `3.0.0.x`：V3-P0 对应的资料包切分闭环基线。
- `3.1.0.x`：V3.1，对应数据看板工作台。
- `3.2.x.x`：V3.2，对应临床数据集阶段、资料清单、访视资料和体验修正。
- `3.3.0.x`：V3.3，对应试验方案解析、版本留痕和项目配置初始化。
- `3.4.0.x`：V3.4，对应图像数据管理、研发副本下载和电子报告上传。
- `3.4.2.x` 至 `3.4.7.x`：V3.4 UI 与访视路线，对应品牌骨架、驾驶舱、资料中枢、方案解析、后台管理和方案访视生效。
- `3.5.x.x`：V3.5，对应字段提取、SSU 字段核查、识别准确率和结肠资料包/大图像包支持。
- `4.x.x.x`：V4，对应服务研发中心算法需求的临床数据资产化体系、Subject Snapshot、Image Evidence、Snapshot JSON 导出和后续算法/数据集资产扩展。

## 3. V1 记录

V1 的目标是形成可运行、可部署、可继续迭代的系统基线。

已完成：

- 前端 React/Vite 应用框架。
- 后端 FastAPI/API 框架。
- PostgreSQL、SQLAlchemy、Alembic。
- 用户、角色、权限。
- 项目、中心、阶段、模板、字典等基础主数据。
- 临床资料上传和资料项管理。
- 文件版本、基础审核记录和操作日志。
- PDF 资料包上传、OCR 识别和初步拆分。
- Mac 本地开发环境与 Linux 生产交付环境分工。
- Linux GPU OCR 生产部署基线。

V1 生产 OCR 基线：

- `PaddlePaddle GPU 3.3.1`
- `PaddleOCR 3.3.1`
- CUDA wheel 源：`cu129`
- Linux 生产 OCR 设备：`gpu:0`
- 生产交付方式：离线镜像包 + 离线模型缓存包

Mac 本地开发 OCR：

- 使用 Apple Vision OCR 服务。
- 默认端口 `8048`。
- 只用于开发和样本调试，不替代 Linux GPU OCR 生产基线。

## 4. V2 记录

V2 的目标是完成“审阅 PDF -> 标记问题 -> 生成任务 -> 上传整改 -> 复审关闭”的闭环。

已完成：

- PDF 在线预览。
- PDF 页面画框批注。
- 批注保存、刷新和回显。
- 根据批注生成整改任务单。
- 上传人根据任务重新上传整改文件。
- 整改文件生成新的文件版本。
- 审核人复审通过或再次退回。
- 整改任务列表和整改任务详情页。
- 全链路操作日志和版本追溯。

关键决策：

- 批注对象绑定拆分入库后的 `files` / `file_versions`。
- PDF 批注结构化保存到 `pdf_annotations`。
- 坐标使用 0-1 归一化坐标，避免缩放偏移。
- 整改任务采用原任务循环，复审不通过时同一任务再次退回。
- 资料包 `pdf_packets` 继续负责上传、OCR 和拆分，不承载 V2 批注闭环。

验收记录：

- 后端 PDF 审阅闭环测试通过。
- 后端全量测试通过。
- 前端 lint 和 build 通过。
- Safari、Chrome、夸克均完成 PDF 审阅生产构建复测。

- 强制重新识别覆盖人工结果。
- 人工拆分、合并、页码修正、资料项修正、确认冻结。
- 前端资料包页面工作台化。

`010005.pdf` 当前验收状态：

- 用户实际测试：通过。

### 6.1 `010001.pdf` 结论

`010001.pdf` 已完成观察验证。它没有推翻 V3-P0 的系统闭环，暴露的问题是现有资料分类和板块体系不准确。

当前结论：

- `010001.pdf` 不准确不是系统能力失败。
- 偏差主要来自前期资料分类、资料板块和审核布局定义不足。
- 不继续在 V3-P0 内用零碎关键词修补解决。
- 后续进入 V3.2 分类与布局方向，先重塑资料分类和审核布局。

## 7. 当前发现的问题

2026-05-21 至 2026-05-22 测试反馈：

识别问题不只是“某一页 OCR 或分类不准”，更核心的问题是前期资料分类、板块/分组和审核布局定义不准确。

这意味着后续判断要从三层拆开：

| 层级 | 含义 | 当前动作 |
| --- | --- | --- |
| 板块 | 临床审核视角下的一组资料范围 | 需要重新重点观察和收敛 |
| 资料项 | 系统入库和审核使用的标准项 | 应与板块对应，但不强行一页一项 |
| 片段 | PDF 资料包切分出来的连续页范围 | 可由人工拆分/合并修正 |

当前优先级：

1. 先确认板块定义是否合理。
2. 再确认资料项映射是否合理。
3. 最后才调分类规则和 OCR 标准化细节。

### V4.0.0 临床数据资产化与 Subject Snapshot 基线

V4 大版本定位为服务研发中心算法需求的临床数据资产化体系。目标不再是单纯生成一份 subject JSON，而是把受试者资料、字段、图像和报告沉淀为可追溯、可复现、可交付的数据资产。JSON 是 Snapshot 的导出形式，不是系统核心资产本身。

V4.0.0 的主要内容：

1. 明确 V4 采用 `Asset First`：核心资产围绕 `Project`、`Subject`、`Snapshot`、`Image Evidence`、`ReportImage`、`AlgorithmRun`、`Dataset` 展开。
2. 明确 V4 采用 `Snapshot First`：正式研发交付必须基于不可变 Snapshot，禁止直接使用实时库状态作为训练或研发交付来源。
3. 明确 V4 采用 `Subject Oriented`：所有资产最终归属于 Subject，并保留项目、中心、筛选号等业务编码标识，不导出姓名、身份证等直接身份信息。
4. 明确 V4 采用 `Historical First`：必须兼容 `C10000` 和 `C200CN` 既有资产；允许新数据更丰富，但不要求历史数据补齐到新项目标准。
5. 定义 Snapshot JSON v0 导出结构：顶层包含 `schema_version`、`generated_at`、`snapshot_id`、`project`、`center`、`subject`、`clinical_tree`、`fields_index`、`images_index`、`source_documents`、`algorithm_runs`、`quality_summary`。
6. 明确字段全量导出：`confirmed`、`extracted`、`needs_input`、低置信、人工修改字段均保留，并用状态、置信度和来源证据区分。
7. 明确图像不内联进 JSON，短期只记录原包、解压目录、报告图片、医生标注图、位置首帧图和必要轻量候选索引。

V4.0.0 定调时的数据基础：

- `subjects`、`subject_sections`、`subject_items` 已能表达受试者、访视和资料项。
- `file_assets`、`file_versions` 已能表达文件和版本。
- `document_extracted_fields` 已能表达文件/片段字段证据。
- `subject_image_records` 已能表达原始图像、增强图像和电子报告记录。

V4.1.5 后的剩余差距：

- V4.1 已补齐受试者级 Snapshot 主表、预检、单受试者生成、JSON 下载和历史管理，但尚不支持批量生成或训练包目录。
- V4.1 的 `images_index` 只表达 raw/enhanced/report 包级信息，尚不表达逐图证据资产。
- V4.2.1 已补齐 PDF 报告图片索引，但尚无医生标注图识别和 Landmark Image 反查能力。
- 无 Landmark Image 所需的轻量候选索引，当前无法稳定从报告时间点反查位置首帧。
- 无算法运行结果模型；病灶资产、训练集导出和算法结果回写不属于 V4.1/V4.2 短期范围。

4.x 路线：

- `V4.0.0`：资产架构、Subject Snapshot、Image Evidence、Snapshot JSON 导出方案、现状差距、路线和验收口径。
- `V4.1.x`：Subject Snapshot 数据模型、生成前校验、单受试者快照生成、Snapshot JSON 导出、快照历史管理和系列收口。
- `V4.2.x`：Image Evidence Index，V4.2.0 建立数据模型，V4.2.1 完成 PDF 报告图片索引，后续覆盖医生标注图、位置首帧图和 Landmark 轻量候选索引。
- `V4.3.x`：Report-derived Lesion Draft，基于报告结构化信息和医生标注图生成病灶草稿资产。
- `V4.4.x`：Algorithm Result Asset，接入算法运行结果、模型版本和增强图回写。
- `V4.5.x`：Dataset Builder，建立研究数据集与训练数据集构建能力。

### V4.1.4 Snapshot 快照历史管理

V4.1.4 是 V4.1 系列的第五个实现版本，在受试者详情页形成 Snapshot 历史管理闭环。

V4.1.4 的主要内容：

### V4.1.5 Subject Snapshot 系列收口与 V4.2 衔接

V4.1.5 是 V4.1 系列的收尾版本，不扩展新的产品能力，只把 V4.1.0-V4.1.4 的 Snapshot 能力整理为稳定基线，并明确 V4.2 从 Image Evidence Index 开始。

V4.1.5 固化的 V4.1 接口清单：

```text
POST /api/subjects/{subject_id}/snapshots/precheck
POST /api/subjects/{subject_id}/snapshots
GET  /api/subjects/{subject_id}/snapshots/{snapshot_id}/json
GET  /api/subjects/{subject_id}/snapshots
```

V4.1.5 固化的 V4.1 数据模型口径：

1. `subject_snapshots` 是 V4.1 的快照主表，负责不可变快照版本、状态、文件路径、hash、大小和生成/锁定信息。
2. `snapshot_quality_checks` 是 V4.1 的快照质量检查表，负责预检运行结果和生成成功后的 Snapshot 关联。
3. V4.1 不再增加 Snapshot 相关表；Image Evidence、AlgorithmRun、Dataset 和病灶资产进入 V4.2 以后。

V4.1.5 固化的 Snapshot JSON v0 口径：

- JSON 来自已生成并锁定的 `released_snapshot`，不能在下载时从实时库临时拼装。
- `clinical_tree`、`fields_index`、`source_documents` 和 `quality_summary` 是 V4.1 的核心输出。
- `images_index` 在 V4.1 只表达 `subject_image_records` 的 raw/enhanced/report 包级信息，包括原包、解压目录、数量、大小和扩展名统计。
- V4.1 不包含 V4.2 的逐图证据索引、Landmark 候选索引、医生标注图资产或报告图片拆分资产。

V4.2 衔接口径：

- V4.2.0 从 Image Evidence 数据模型开始，输入基础是现有 `subject_image_records`、Snapshot JSON `images_index` 和原始/增强/报告包状态。
- V4.2 的短期目标是 Image Evidence Index，优先服务报告图片、医生标注图、位置首帧图和 Landmark 轻量候选索引。
- V4.2.0 不做训练包导出、不做算法运行结果、不做病灶资产、不做完整逐图训练集流水线。
- V4.2.0 只固化 `image_evidence_index` 基础字段；V4.2.1 负责 PDF 报告图片索引，Landmark 和 marked image 规则仍留在后续阶段。

验收口径：

- V4.1.0-V4.1.4 不再被描述为未来规划，统一作为已落地 Snapshot 基线。
- V4.2.0 写成数据模型阶段，V4.2.1 写成已落地报告图片索引；Landmark 反查和导出仍是后续阶段。
- 静态搜索不得出现本版本新增 Image Evidence、AlgorithmRun、Dataset 或病灶资产模型的实现口径。

边界：

- 不新增后端 API，不新增前端路由或按钮。

### V4.2.0 Image Evidence 数据模型基线

V4.2.0 是 V4.2 系列第一个实现版本，只建立 Image Evidence Index 的持久化和内部类型基础。

V4.2.0 的主要内容：

2. 预留 `raw_package`、`enhanced_package`、`report_package`、`report_image`、`marked_image`、`landmark_image` 六类证据类型。
3. 预留 Landmark 匹配状态：`resolved`、`approx_matched`、`unresolved`、`not_supported`，并允许为空以兼容非 Landmark 证据。
4. 新增 `ImageEvidenceIndex` ORM 和 `ImageEvidenceIndexRead` 内部 schema，供 V4.2.1-V4.2.3 复用。

### V4.2.1 报告图片索引基线

V4.2.1 在现有 `image_evidence_index` 上建立当前电子报告版本的可重建图片证据索引。

主要内容：

1. PDF 电子报告上传成功后，使用 PyMuPDF 自动提取内嵌栅格图片，原报告始终保留。
2. 每个报告版本生成一条 `report_package`；按 SHA256 去重后的图片生成 `report_image`，重复出现位置记录在 `payload_json.occurrences`。
3. 图片保存到报告版本目录的 `evidence/report_images/`，索引保留页码、图片序号、xref、宽高、扩展名、MIME、hash 和大小。
4. 新增 `POST /api/image-data/{record_id}/report-images/index`，供历史报告补建和失败重试；重建采用替换语义。
5. 报告重传或删除时同步清理旧索引和提取图片。PDF 无图、格式不支持或解析失败不会撤销报告上传。

索引状态：

- `indexed`：提取出至少一张去重图片。
- `empty`：PDF 合法但没有内嵌图片。
- `not_supported`：当前为 DOC、DOCX、XLS 或 XLSX；仍保留电子报告。
- `failed`：PDF 损坏或解析异常；错误写入包级证据和 `parse_warning`。

边界：

- 所有提取图片统一记为 `report_image`，不使用启发式规则猜测 `marked_image`。
- 不做 Landmark 反查，不改变 Snapshot JSON，不新增前端入口或数据库 migration。
- 不建立原始/增强图像逐图索引，不做 Image Evidence 导出、病灶资产、训练集或算法结果回写。

### V4.2.2 Landmark Image 反查基线

1. PDF 报告图片通过 OCR 获取烧录经过时长，通过图片上方标题获取消化道位置。
2. raw 原包优先读取 `ispLog.txt` 确定首帧时间，文件名最小帧作为回退。
3. 仅扫描目标秒前后候选，以 OpenCV 遮罩时间文字和绿色圈注后计算相似度。
4. 命中的增强图按同文件名回溯 raw，同步写入 `landmark_image`；绿色圈注报告图写入 `marked_image`。
5. 支持重建、查询、受控图片预览、候选切换和人工确认；任一图像资料换版后旧结果失效。
6. 图像单文件上传上限统一提升至 `4096MB`，生产 Nginx 对应为 `4g`。

边界：

- 不建立全量逐图数据库索引，候选只保存在 Landmark payload。
- 不修改 Snapshot JSON，不做 Image Evidence 导出、病灶资产、算法结果或训练集。

### 历史分类与布局方向

以下内容是 V3-P0 收口时形成的历史改进方向。字段提取已在 V3.5 落地，不能再把本节理解为当前版本前置条件：

1. 重塑资料分类体系。
2. 重塑资料板块/分组体系。

## 10. 生产变更原则

- 生产变更前必须备份数据库和文件存储。
- 数据库结构变更必须走 Alembic migration。
- 后端 Python 文件替换后必须重启 backend。
- 前端静态资源或镜像替换后必须重启前端/Nginx 或确认资源刷新。
- OCR 服务代码或镜像变化必须单独验证 `/health` 和真实样本。
- Mac Apple Vision OCR 只用于本地开发，不替代 Linux GPU OCR 生产基线。
